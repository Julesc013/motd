# MOTD 0.4: presentation, portability and evidence

Status: implemented behavior and release acceptance contract. The dated
[audit](../docs/audit-2026-11-17.md) and `build/verification-*-v04.json` records
separate observed results from remaining compatibility targets. Version 0.4
extends schema 1; an older recipe continues to choose Bash and classic layout.

## 1. Product boundary

One Python configurator creates standalone system messages. It accepts validated
TOML recipes, offers equivalent CLI and terminal-wizard paths, generates scripts
or static notices, and manages explicitly supported Linux attachments. Normal
generated output does not need Python, a daemon, a package service or network
access. Hooks are explicit user configuration.

“Universal” is a direction for adapters and evidence, not a release claim. The
output interpreter, OS collectors, terminal capabilities and login attachment
are four separate compatibility dimensions. Missing data must remain visibly
unavailable; a script running is not proof that every metric or integration is
supported. See [compatibility](compatibility.md).

## 2. Presentation model

| Setting | Contract |
|---|---|
| `display.design` | `classic`, `cards`, `ledger`, `briefing`, `dashboard`. |
| `display.density` | `compact`, `balanced`, `comfortable`; spacing/allocation preference. |
| `display.detail` | `brief`, `normal`, `full`; requested content depth. |
| `display.padding` | Horizontal inset preference 0–3. |
| `display.section_gap` | Blank-row preference 0–2. |
| `display.color_emphasis` | `quiet`, `balanced`, `vivid`; independent of palette. |
| `display.sections` | Unique enabled IDs in display order. |
| `display.priority` | Unique retention/expansion IDs; omitted enabled IDs follow in display order. |
| `display.section_detail` | Per-section brief/normal/full overrides. |
| `display.width`, `display.rows` | 40–240 columns, 8–200 total rows. |

The allocator preserves a prompt row, reduces optional detail before dropping
sections, omits whole sections rather than clipping open frames, and names
omissions. Density adjusts gaps; fewer retained bands need fewer gaps. Padding
remains the requested inset. Retention priority does not change display order;
briefing deliberately puts an enabled Attention section first. Custom retention
priority can omit Attention; the default protects it first.
Unavailable observations never become zero or “healthy” merely to fit a design.
The five structures use the same observations and collection paths.

Classic retains familiar framing. Cards isolate sections. Ledger uses open
aligned rows. Briefing promotes readable summaries and retains meaningful first
detail rows. Dashboard pairs panels when width permits and stacks otherwise.
Density and detail remain independent: comfortable/brief and compact/full are
both valid. Terminal constraints can reduce requested spacing or content.

Colour and character-set switches retain existing precedence: explicit plain
mode, `NO_COLOR` and the mono palette disable colour. Historical byte-oriented
engines normalize unsupported characters rather than claiming full Unicode
grapheme/cell behavior. Geometry tests must use both ASCII and Unicode routes.

## 3. Shared implementation

- Canonical `runtime/motd.bash`, `runtime/motd.sh`, `runtime/motd.ps1` and
  `runtime/designs.sh` are embedded by `tools/embed_runtime.py`.
- Bash and portable sh reuse the POSIX design engine through small data/row
  adapters. PowerShell implements the same configuration contract natively.
- Zsh dispatches to an available Bash/sh engine; Fish launches the portable
  `/bin/sh` body. These are declared dependencies, not independent collectors.
- CMD launches its embedded PowerShell body and requires the relevant
  `ScriptBlock.Create` capability. Its PS2+ target is separate from direct
  PowerShell1-era syntax compatibility.
- `batch-text` is a literal ASCII Windows NT CMD notice, with escaped echo data,
  no collectors and no hooks. It is not DOS/COMMAND.COM certification.

The Fish payload has a 96,000-byte limit. Larger configurations should select a
direct sh output. Static text, issue and SSH-banner routes retain their distinct
consumer/escaping contracts. No new general plugin ABI or layout language is
introduced.

## 4. Wizard behavior

The screen interface reserves ten control rows for questions, answers, help and
navigation. It allocates the remaining rows to actual generated demo output and
remeasures the terminal while waiting for an answer. Geometry overrides are
temporary and do not overwrite the saved recipe. Resizing retains typed input.

Choices have descriptive labels, context help (`?`), visible navigation keys and
number/arrow selection. Long menus/help paginate. The driver writes changed rows
in one buffered refresh, clears the screen only on initial draw or a geometry
change, and restores input/console mode on exit. Windows input/VT support is
capability checked; unsuitable consoles use line mode.

Hooks are hidden from preview by default. `H` toggles samples only; `J`/`K`
scroll them. Fastfetch, literal text and explicit `preview_text` never execute
while browsing the wizard. The selected interpreter must be present to preview
its output. Caching avoids identical repeated work; cold PowerShell startup is
not promised to be instantaneous. Native interactive-console UX evidence is
distinct from redirected CI execution.

## 5. Configuration and commands

CLI display options mirror saved settings. Runtime options can override design,
density, detail, padding, gaps, emphasis, geometry, colour and character set.
Section lists/order/priority and per-section detail are generation settings.
Unknown values, duplicate IDs, malformed inline tables and numeric injection
attempts must fail validation before output or hook execution.

Before/after calls retain argv arrays, timeout and failure policy. The reserved
`motd:print` operation writes literal lines with no external process or shell
interpretation. Normal output backpressure applies to these writes. Arbitrary
programs remain explicit executable configuration; historical direct-process
termination is not a sandbox or a universal descendant-tree deadline.

Opaque executable imports require an explicit target and interpreter. Inspection
does not execute them. Reconfiguration requires a real recipe; exact imported
bytes cannot acquire a new design by changing metadata alone. Trusted opaque
live execution retains its documented side-effect boundary.

## 6. Python and filesystem boundaries

The generator supports Python 3.8+. Python3.11+ uses standard-library `tomllib`;
older supported versions use embedded readable Tomli2.3.2 with its MIT licence
and archive provenance. `tools/embed_toml.py --check` verifies synchronization.
Actual Python3.8 execution, parsing and lifecycle tests are required; an AST
grammar parse alone is insufficient. Python3.0 is not a target for this release.

Linux managed installation retains descriptor-based path checks, private state,
before/after archives, a write-ahead progress journal, drift detection, repair,
rollback and recovery. Individual file replacement is atomic; the multi-file
operation is journalled, not globally atomic. ACL/xattr preservation and
exclusion of noncooperating writers are not claimed.

Cross-platform export is create-only in existing trusted directories. It
refuses overwrites, writes content hashes in a final manifest, and compensates
ordinary failures only for new files with matching identity and bytes. It has
no managed-install ownership, overwrite recovery, crash journal, ACL restore or
hostile-parent-directory guarantee. Windows chooses this route automatically.

Source reads are regular-file-only and bounded to2MB. Managed-file snapshots are
bounded to16MiB per file before and during reads. Terminal-control/newline paths
are rejected. These checks happen before planned filesystem mutation.

## 7. Evidence and release gates

Required evidence includes:

- Synchronized embedded source and parser; shell syntax checks; focused
  configuration, quoting, transaction, import, wizard and geometry regressions.
- Actual Python3.8 plus the ordinary development interpreter.
- Actual historical Bash/Zsh and available fish/ash/ksh engines, with exact
  version, OS, command, runtime-source hashes, qualifications and failures.
- Native Windows PowerShell5.1, Windows PowerShell7 and macOS PowerShell7 jobs.
  A separate exact-version PS2 probe must identify actual major2 before recording
  a pass; an absent engine is blocked, never silently replaced by5.1/7.
- The portable historical PowerShell harness can run on user-provided legacy
  Windows VMs without Python. PS1/3/4/5.0 claims remain unverified until actual
  engines complete suitable checks; syntax review is recorded separately.
- The524-case classic gallery and140-case design sampler preserve recipes,
  PTY transcripts, source/engine hashes and complete terminal grids at40×25,
  40×50,80×25 and80×50. Every image must pass wrap/scroll/prompt-row checks and
  lossless decoded-pixel verification after compression.

The matrix is bounded evidence, not proof of every combination of design,
character set, terminal, operating system and historical patch release. New
failures become regression cases where they affect behavior; tests should not
mirror private implementation details merely to inflate coverage.

## 8. Continuation

The [roadmap](../ROADMAP.md) sequences legacy engine evidence, native installation
adapters, real terminal-host UX, collector accuracy and performance work. Each
new attachment needs a read-only plan, explicit ownership, a reversible strategy,
native-host verification and an honest unsupported path. Prefer extending the
shared model over adding another renderer or duplicating collectors.
