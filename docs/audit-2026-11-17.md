# Portability, presentation and architecture audit

Audit date: **17 November 2026**. Baseline: commit `8951c44` (version 0.3.0).
The implementation review also covers the subsequent `feat/designs-and-portability`
work. A source-level finding and an executed test are different evidence; the
verification section identifies that boundary explicitly.

## Outcome and intended product

The useful goal is a small, portable configurator that exports readable,
standalone MOTD programs, with consistent choices and honest capability reporting.
It is not possible to certify every operating system, distribution, terminal,
shell minor version and login integration by adding interpreter version checks.
The project should publish verified combinations, supported syntax targets and
known unavailable capabilities separately.

Keep the current distribution model: one downloadable `motd.py`, TOML recipes,
canonical runtime sources, and generated outputs that do not need Python at
login. Build-time embedding is appropriate here. A package server, daemon,
configuration database or extensible plugin host would add installation and
maintenance work without solving the requested MOTD use case.

The highest-value changes in this review are actual alternative presentations,
independent spacing/detail controls, a practical older Python floor, native
Windows file export with a deliberately narrower safety contract, and evidence
that follows the exact source being released.

### Requested vision that is still not implemented

| Part of the wider vision | What exists now | Missing behavior / next acceptance condition |

| Configurable persistent shell prompts | A greeting, display-only hints and explicit before/after calls | No managed Bash `PS1`/`PROMPT_COMMAND`, Zsh prompt/precmd, Fish `fish_prompt`, PowerShell `prompt`, or CMD `PROMPT` integration. Any future adapter must preserve existing prompt customization and avoid recollecting an entire dashboard before each command. |
| Per-command or contextual hints | A recipe can show commands and notes in the MOTD | No command-entry interception, completion/prediction integration, command-specific advice engine, or prompt-side hint event. Displayed hints do not execute themselves. |

| Managed Windows profiles/startup/sign-in routes | Native PowerShell/CMD output, static batch text, create-only exports | No automatic `$PROFILE`, CMD AutoRun, registry, Group Policy, RDP desktop notification or Windows sign-in-policy installation. A future installer needs its own native path/ACL/journal contract and explicit route selection. |
| Every Unix shell, including older Bourne, csh and tcsh | Bash, Zsh delegation, Fish delegation and a POSIX-like sh core | No native csh/tcsh recipe target or managed startup adapter. Non-POSIX Bourne dialects are not certified by dash or modern ksh/ash tests. Manually invoking an existing compatible sh output does not establish a native adapter. |
| Every pre-login/remote consumer | Static issue, SSH-banner and generic text exports; guarded interactive shell attachment on Linux | BSD gettytab, BusyBox getty options, distro-specific PAM/update-motd, Telnet banners, RDP and Windows policy routes need separate tested adapters. Exported text does not configure those services. |
| Every historical PowerShell and original OS | Exact-engine harness, contemporary native CI, preserved historical engine evidence | PS1, PS3, PS4 and PS5.0 still need actual hosts/VMs. The retained PS2/Server2022 run establishes that engine/host combination; it does not establish the original PS2-era OS. |
| Native Windows live wizard resizing | A Windows input implementation and pure frame rendering | A real console still needs a manual resize/partially typed answer check, plus old-console line-mode fallback. The Unix PTY test and native export tests do not establish this. |

These are concrete omissions from the broader vision, not hidden features of
`hooks`, `hints`, static text or the word “portable.” The current release can be
complete for its declared generation/presentation/export scope while this wider
integration work remains open.

## Findings, severity and resolution boundaries

Severity describes impact in this project, not an external vulnerability score.
P1 blocks a material promised workflow or can misrepresent safety; P2 is a
bounded correctness, portability or maintenance issue; P3 is an improvement.

### P1 — Windows export previously entered a POSIX-only transaction path

At the baseline, `export_files`, `save_recipe` and recovered-config output all
used the POSIX transaction engine. A Windows user could generate stdout but could
not use those ordinary output-file workflows. Read-only import also called a
POSIX file helper. This was a real boundary, not fixed by a PowerShell script
passing tests on Linux.

The new read-only path checks a bounded ordinary file and its identity. New-file
export uses exclusive creation, refuses existing destinations and observed
symlink/reparse parents, records recipe/artifact hashes, and compensates only
files whose captured identity and exact bytes still match. Failure preserves an
externally changed new file rather than deleting it.

This is **create-only export into an existing trusted directory**. It has no
install ownership, overwrite, rollback journal, crash recovery or ACL restoration.
Path-based parent checks cannot reproduce the POSIX engine's pinned directory
handles against a hostile directory-swap race. A future Windows installer needs
an explicit native handle and ACL design; reusing this helper for installation
would weaken the existing contract.

### P1 — A universal support claim would exceed the available evidence

The evidence includes real old Bash/Zsh engines, actual PowerShell 2.0 and modern
Linux, macOS and Windows jobs. It does not include every historical Windows PowerShell
engine, original historical Unix OS, BusyBox build, Windows terminal host, or
real SSH/PAM/getty deployment. A successful parser check only establishes syntax
acceptance; a synthetic render establishes layout; neither proves live collection
permissions or login integration.

Retain exact engine/OS versions, source hashes and skips. Keep a separate manual
or self-hosted legacy PowerShell harness where hosted CI cannot supply old
engines. Mark those rows unverified until its output is actually available.
Capability failures must remain unavailable/partial/stale, never silently become
zero or healthy values.

### P1 — Before-calls ran before invalid Bash arguments were rejected

The generated Bash wrapper previously ran configured before-calls before the
renderer parsed its arguments. A malformed width or design option could therefore
produce side effects before exiting with an argument error. Parsing in the Python
configurator did not protect a subsequently invoked generated script.

The Unix runtime now exposes a private validation-only entry path, and the
generated wrapper checks arguments, registry and layout settings before running
configured calls. That path collects no host observations and does not run hooks.
The Unix regression suite checks that invalid options leave a sentinel untouched.
This is a correctness fix to execution order, not an authorization restriction
on valid explicitly configured calls.

### P2 — Python 3.0 is not a small compatibility adjustment

The existing program uses f-strings, `pathlib`, modern exceptions, subprocess
timeouts and POSIX descriptor-relative filesystem APIs. Python 3.0 cannot even
parse f-strings, which were added in Python 3.6. A complete 3.0 rewrite would also
require replacing library interfaces and revalidating the transaction engine;
lowering a version guard would be incorrect. [Python's 3.6 release notes][py36]
document the syntax change.

Python 3.8 retains the current design with a bounded TOML fallback. The selected
Tomli 2.3.2 is MIT-licensed, supports Python 3.8+, and parses TOML 1.0. Its source
and archive SHA-256 are retained in `vendor/tomli/provenance.json`. The embedding
tool removes only package-relative/future import wiring and wraps otherwise
inspectable Python in a factory; it does not encode or dynamically execute the
parser. [Tomli's release metadata][tomli] and [stdlib `tomllib` documentation][tomllib]
provide the upstream contracts.

The portable recipe contract is TOML 1.0. A future standard-library parser may
accept additional syntax; that alone must not silently widen the recipe format
promised to Python 3.8 users. Generated recipes should remain in the declared
common format and round-trip through both parser paths.

Python 3.8 compatibility is useful for existing machines, not a recommendation
to install an unsupported interpreter. Python's status table records 3.8's end
of life as 7 October 2024. Python 3.11's Windows documentation identifies 3.8 as
the line for Windows 7; that is an interpreter boundary, not proof this project's
wizard/export has run on Windows 7. Generate on a maintained machine and copy
the standalone output when that is the simpler deployment. [Python version
status][pystatus]; [Python on Windows][pywindows].

### P2 — Import metadata is integrity evidence, not authentication

An embedded recipe and digest allow accidental edits to be detected and a known
recipe to be regenerated. Anyone who can change the entire artifact can also
replace its recipe and digest. Import inspection must not treat the digest as a
signature or execute the artifact to discover its settings.

The safe preview path regenerates from a validated recognized recipe and
suppresses calls. A trusted live run of opaque imported code is explicitly a
different operation. Opaque shell imports should require an explicit interpreter
as well as target, because a default Bash selection is not evidence about the
input's language. Static notices do not all carry a recoverable recipe; keep the
recipe alongside those files. Regeneration with a newer generator may produce
different bytes, so exact historical reproduction also needs the original
artifact and generator revision.

The current CLI now requires `--shell` for an opaque `--target shell` import.
Bounded `_source_text` reads also move the size check before unrestricted input
allocation. Both fixes should retain their explicit negative CLI tests.

### P2 — Transaction guarantees need their actual metadata and memory limits

The POSIX engine checks path ownership and drift, pins parents, stages replacement
bytes, journals progress and compensates reversible failures. It records mode,
UID and GID. It does not preserve arbitrary ACLs, extended attributes, security
labels, alternate streams or every filesystem-specific property. It cannot lock
out a noncooperating writer merely by owning its own journal lock.

Imported/configuration reads now reject more than 2 MB before opening and retain
a bounded stream read if the file grows. Transaction snapshots now reject targets
larger than **16 MiB**, both from the initial size and from the streaming total
before accumulating more bytes. This resolves the previously unrestricted target
backup allocation. The path-safety tests exercise the limit and failure behavior;
the ceiling is intentional, so unusually large installation files are refused.

Managed path validation also rejects newlines and C0/C1 terminal control
characters. Such a path could otherwise break startup block markers or alter
what a terminal review appeared to show. Ordinary spaces and quoted shell
metacharacters remain legitimate path data and require the actual target
interpreter's quoting rules.

No test should call multi-file replacement globally atomic. Crash-injection and
temporary-directory tests verify the journal algorithm; real login deployments,
root ownership restoration and unusual filesystems require their own evidence.

### P2 — Presentation must not alter observation meaning

The new shared Unix design engine accepts already-collected section rows and
owns framing/spacing. It does not introduce new collectors or execute configured
hooks. The PowerShell equivalent operates over its existing section model. This
keeps presentation changes from multiplying live sampling paths.

The largest remaining drift risk is semantic duplication between full Linux,
portable Unix and PowerShell collectors. CPU intervals versus lifetime averages,
process RSS, physical disk activity versus per-process counters, and permission
coverage must stay accurately labelled. Shared fixtures and explicitly documented
capabilities are a smaller solution than an abstract plugin framework.

Readability needs more than a row-count assertion: short screens must show whole
frames and understandable omission text; default priority protects attention,
while explicit custom priorities control retention. Long screens should use
meaningful additional detail when the requested detail level allows it. Fixed
padding and density-adjusted gaps count against the budget; the planner normally
trims detail before omitting sections, rather than silently removing requested
spacing. The bounded style sampler and
native-engine tests provide complementary evidence. A colored border alone does
not establish a different layout.

The first style sampler also caught a concrete context-loss bug: Bash ledger and
wide dashboard could show domain/IP and capacity without hostname or uptime, and
their header paths could lose the demo label. This is why final visual QA checks
the identity/mode context as well as cell geometry. The corrected Unix adapters
carry host/uptime context through these presentations and lead demo titles with
an explicit marker. Final-source narrow/wide comparison sheets and representative
PowerShell/dashboard frames were visually checked after the correction.

### P2 — Release evidence can go stale while still looking complete

The old gallery's 524-case manifest and older passing test logs remain historical
records after source changes. They cannot be cited as a pass for new code. The
gallery verifier checks both source hashes and regenerated artifacts; source
coverage must include `runtime/designs.sh`, not only files matching `motd.*`.

Keep one clearly named current-release verification record and retain older
records with their version/source scope. Re-run the final matrix only after
renderers and generator are frozen. Do not combine old test totals with new
test cases or turn skipped legacy/Windows cases into inferred passes.

### P3 — One-file distribution should not mean one-file maintenance

At baseline `8951c44`, `motd.py` measured 346,609 bytes and 6,706 lines; 2,702
lines preceded embedded runtimes. The canonical Bash, sh and PowerShell files
were respectively 2,822, 527 and 641 lines. These are measurements of that
revision, not estimates of the new release. Most distribution-file size is
inspectable embedded runtime source.

Keep canonical sources separate and synchronization mechanical. The configurator
still combines schema/serialization, generation, transactions, CLI and wizard;
that is manageable with named boundaries and focused tests. Extract another
canonical source only when changes demonstrably collide or a unit has a stable
interface. Avoid a generic packaging/framework rewrite merely to make the line
count smaller. The plain bundled TOML parser adds an intentional vendored
component with provenance, license and an update procedure.

The project also needs an owner decision on its own license. A vendored MIT
license applies to that component; it does not choose licensing terms for the
rest of the repository or historical reference material.
